# EPlayerServer 系统学习路线

EPlayerServer 是一个 Linux C++17 HTTP 登录服务。主进程接入连接，业务子进程解析和校验，日志子进程接收记录并写文件。理解它的关键，是把进程、线程、连接、请求、数据库行这几种不同寿命的对象连接起来。

本套讲义采用阶段式组织：先交代问题与运行主线，再解释机制和接口参数，接着用具体数据推演，最后定位当前源码及失败路径。讲解围绕当前工作区的实现，不把课程中的旧实现或其他项目的能力当成已有功能。全部知识解释放在正文中，没有单独实验目录或作业要求。

## 1. 项目最终完成什么

客户端发送：

```text
GET /login?time=...&salt=...&user=...&sign=... HTTP/1.1
```

服务器解码参数，按 user 查询 MySQL，从唯一用户记录中取出密码字符串，计算 `MD5(time + key + password + salt)` 并比较，最后返回 HTTP 和 JSON。成功时 JSON 的 status 为 0，失败时为负数。

当前服务没有视频播放、视频传输、注册、token 或后续会话功能。源码中的 SQLite 是另一种数据访问实现，正常登录主线选择 MySQL。

## 2. 阅读时固定区分的六个问题

| 观察点 | 在本项目中怎样落实 |
| --- | --- |
| 代码的位置 | 文件、类和函数分别在哪里 |
| 执行的位置 | 父进程、业务子进程、日志子进程；各自哪条线程 |
| 数据的意义 | 字节片段、完整 HTTP、URL 参数、数据库行或业务状态 |
| 状态的归属 | 线程局部、单连接、线程池共享或数据库连接共享 |
| 资源的责任 | 哪个对象负责删除，哪条路径负责 close、join、wait |
| 成功的边界 | 创建成功、已入队、消息发出、业务完成和资源回收各指什么 |

例如，AddTask 返回 0 只表示任务入队；SendSocket 返回 0 只表示转交通道接受消息；HTTP 200 也不表示登录成功。这些结论分别来自不同接口，不能把“成功”视为全程序统一的一种状态。

## 4. 三条阅读路径

首次完整阅读按 00 至 11 前进。00 先建立大图，01 补语言和构建基础，02 至 05 解释支撑设施，06 至 09 沿字节与业务数据推进，10 解释收尾，11 把机制归纳为设计。

如果主要关心架构，可先读 **00 → 04 → 10 → 11**，再读 **06 → 07 → 08 → 09** 补齐业务内部。01 至 03、05 可在遇到具体 API 时回查。

如果主要关心一次登录为什么成功或失败，按 **00 → 06 → 07 → 08 → 09** 阅读：先认识请求，再认识表和行，最后理解查库与校验。07 中的 Insert、Modify、Delete 可留待第二遍；登录使用的是 Query 和结果克隆。

## 5. 本项目与 IOCP 参考讲义的关系

组织方式参考 [IOCP 仓库的 docs](https://github.com/slimesq/IOCP/tree/ebb53f0f13a926c2ba63ec094b20fe9864667f9f/docs)：按前置关系逐阶段解释，从接口推进到对象寿命、状态推演和源码映射。阅读本套讲义不要求先了解 IOCP 或 Windows 网络编程。

本项目在 Linux 上使用 epoll 通知就绪，再由线程调用 read/send。讲解采用这一实际模型；与参考项目的异步完成模型有何差别，集中在阶段十一说明。

## 7. 源码和图形约定

“源码片段”直接摘取当前文件，可能是类中的一个成员函数，不能因此当作独立程序编译。“结构示意”会省略细节，用于解释关系。出现一种可能的改造时，正文明确说明它尚未存在于项目中。

函数名和相对文件链接共同用于导航。图形使用 Mermaid，同时提供文本调用链或表格；只看 Markdown 原文也能跟踪。构建、启动、VS Code 操作保留在项目 [README](../README.md)，此处不把工具操作替代为原理讲解。
