# EPlayerServer 阶段九 登录校验与响应封装

本章把前面的协议字段和数据库行接成一次完整登录。重点是每一步输入的字节、分支返回值和响应边界，而非仅记住“调用 MD5”。

源码入口：[EdoyunPlayerServer.cpp](../src/EdoyunPlayerServer.cpp)、[业务表](../inc/EdoyunPlayerServer.h)、[Crypto.cpp](../src/Crypto.cpp)、[JsonCpp](../third_party/jsoncpp/json.h)。

## 1. 业务调用从哪里开始

```cpp
int CEdoyunPlayerServer::Received(CSocketBase* client, Buffer const& data)
{
    return client->Send(MakeResponse(HttpParser(data)));
}
```

Received 在业务工作线程同步执行。HttpParser 返回 int，MakeResponse 返回完整响应 Buffer，Send 消费该 Buffer；外围 ThreadFunc 随后 RemoveClient。

这里没有独立登录线程池，也没有查询完成异步回调。数据库锁等待和实际查询会占用当前处理线程。

## 2. 入口校验的顺序

```text
重新解析完整 HTTP
  → 语法和完成检查
  → 方法必须 GET
  → URL 必须可解析
  → 路径必须 login
  → time、salt、user 非空且 sign 长度 32
  → 查询数据库
  → 恰好一条记录
  → 读取密码、计算摘要、比较
```

顺序决定客户端看到的错误。例如一个缺参 POST 先得到方法不支持，不会先进入缺参检查；不存在用户不会进入摘要计算。

业务函数与 CHttpParser 类同名片段都包含 HttpParser，但职责不同：类处理语法，业务成员方法负责路由、数据库和规则。

## 3. 四个参数的真实含义

| 名称 | 源码当前检查 | 后续用途 |
| --- | --- | --- |
| time | 非空 | 按字符串参与摘要 |
| salt | 非空 | 解码后参与摘要 |
| user | 非空 | 按用户名查库 |
| sign | 长度 32 | 先转小写再比较 |

没有把 time 转数字检查时效，也没有保存已用 salt。长度 32 预检不等于已逐字符验证十六进制，最终比较会拒绝不匹配内容。

user 不直接出现在 MD5 拼接中。它决定查哪条记录，从该记录取出的密码字符串才进入计算。把用户名也拼进去会得到不同协议。

## 4. URL 编码与摘要字节

以 salt 的原始值 `a+b c` 为例：

```text
原始逻辑值：a+b c
URL 参数： salt=a%2Bb+c
解码后：   a+b c
MD5 输入使用解码后内容，不是 a%2Bb+c
```

%2B 表示字面加号，查询编码中的 + 表示空格。若客户端不正确编码字面加号，服务端会得到另一个 salt，摘要自然不同。

Buffer 是字节串，摘要没有自动 Unicode 规范化或额外文本编码步骤。客户端和服务端必须对同一逻辑内容形成相同字节。

## 5. 从 user 到 Result

查询步骤在同一把数据库锁内：

```cpp
std::lock_guard<std::mutex> lock(m_databaseMutex);
Buffer condition = "user_name='" + m_db->Escape(user) + "'";
if (m_db->Exec(table.Query(condition), rows, table) != 0)
    return -3;
```

table.Query 默认列出业务表全部字段，并不只查询密码列。结果映射后释放数据库锁，后续读取的是独立 C++ 行值，不再直接借用 MYSQL_RES。

| rows 情况 | 后续 |
| --- | --- |
| 0 行 | -4 用户不存在 |
| 1 行 | 继续 |
| 多于 1 行 | -5 同名用户异常 |

user_id 是主键，但 user_name 没有 UNIQUE 约束。主键不自动保证用户名唯一，多行分支在当前表结构下确实可能发生。

## 6. 密码字段的访问层次

```cpp
Buffer password = *rows.front()->Fields.at("user_password")->Value.String;
```

```text
rows.front()：第一行的 shared_ptr<_Table_>
  → Fields：按列名定位 PField
  → Value.String：文本字段拥有的 Buffer 指针
  → *：取出 Buffer 内容并复制到局部 password
```

这依赖字段被定义为文本类型。业务直接知道列名、union 表示和具体 MySQL 客户端，说明存储模型还没有被独立用户仓储接口挡住。

## 7. 签名拼接规则

这里称 sign 为“签名”，具体实现是共享约定下的 MD5 摘要比较。摘要把输入字节映射成固定长度结果；服务端通过重新计算来验证，不是把 sign 解密成密码，也没有使用公钥、私钥的数字签名算法。

```text
expected = MD5(time + key + user_password + salt)
```

key 读取 EPLAYER_SIGN_KEY，未设置时沿用源码固定默认值。加号是直接字符串连接，没有分隔符。请求没有单独 password 字段，服务端也不解密 sign，而是独立计算 expected 后比对。

当前直接使用数据库字符串，没有在这里执行密码派生函数 KDF 或从明文重新校验慢哈希的流程。服务端校验结果的一致性，依赖客户端遵守同样的拼接约定。

## 8. Crypto::MD5 的完整实现

```cpp
Buffer Crypto::MD5(Buffer const& text)
{
    unsigned char digest[EVP_MAX_MD_SIZE]{};
    unsigned length = 0;
    if (EVP_Digest(text.data(), text.size(), digest, &length, EVP_md5(), nullptr) != 1)
        throw std::runtime_error("MD5 calculation failed");
    Buffer result;
    char byte[3]{};
    for (unsigned i = 0; i < length; ++i)
    {
        snprintf(byte, sizeof(byte), "%02x", unsigned(digest[i]));
        result += byte;
    }
    return result;
}
```

### 8.1 EVP_Digest 的参数

| 参数 | 当前值 | 含义 |
| --- | --- | --- |
| 输入地址 | text.data() | 待摘要的字节 |
| 输入长度 | text.size() | 不依赖 strlen |
| 输出地址 | digest | 存放原始摘要 |
| 输出长度地址 | &length | 获得实际摘要长度 |
| 算法 | EVP_md5() | 选择 MD5 |
| 最后参数 | nullptr | 不传自定义引擎 |

成功返回值为 1，与项目常见的“0 成功”包装不同。失败抛 runtime_error，当前上层没有统一捕获并转成 JSON 的机制。

### 8.2 16 字节怎样成为 32 字符

MD5 原始输出 128 位，即 16 字节。每个字节以 `%02x` 写为两位小写十六进制，所以长度 32；byte[3] 还为两字符后面的终止零留位置。

`Crypto::MD5("abc")` 的标准表示为 `900150983cd24fb0d6963f7d28e17f72`，也是当前组件验证使用的基础向量。

## 9. 一组假定数据的完整演算

以下值仅用于解释协议，不表示本机数据库已有该账号，也不需要导入数据库：

| 数据 | 示例值 |
| --- | --- |
| user | alice |
| 数据库 password | demo-password |
| key | demo-key |
| time | 1700000000 |
| salt | a+b c |

```text
拼接字节：1700000000demo-keydemo-passworda+b c
摘要：6c96e1487249303395906b98f67fef2d
```

请求目标为：

```text
/login?time=1700000000&salt=a%2Bb+c&user=alice&sign=6c96e1487249303395906b98f67fef2d
```

若库中恰好一条 alice，密码相同，服务端 key 也按示例配置，则得到 0。换一个密码、key 或 salt，expected 都可能改变；直接复制这个 sign 到另一种配置不能保证成功。

## 10. 大小写归一与比较

std::transform 把 sign 每个字符转小写，再以 CRYPTO_memcmp 比较 expected.size() 个字节。这样大小写不同的合法十六进制表示可以匹配。

恒定时间比较的意图是减少普通字符串比较早停造成的时序差异，不会把拼接式 MD5 变成 HMAC，也不会给 time 自动增加时效检查。

## 11. 返回码来自哪一层

| 状态 | 当前触发条件 |
| --- | --- |
| 0 | 摘要匹配 |
| -1 | HTTP 解析失败或不完整；连接层也用它表示累计超限等 |
| -2 | URL 解析失败 |
| -3 | SQL 查询失败 |
| -4 | 没有该用户名 |
| -5 | 同名记录不唯一 |
| -6 | 缺参、sign 长度错误或摘要不符 |
| -7 | 方法或路径不支持 |

正常半包在连接状态中等待，并非每次都返回 -1。对端提前断开等路径直接移除，也不保证生成一份带这些状态的响应。

初始化中的 CServer::Init -3 另有含义，不能因为数字相同就当成这张业务表里的 SQL 错误。

## 12. MakeResponse 的完整结构

```cpp
Buffer CEdoyunPlayerServer::MakeResponse(int result)
{
    Json::Value body;
    body["status"] = result;
    body["message"] = result == 0 ? "success" : "登录失败，可能是用户名或者密码错误！";
    Buffer json = body.toStyledString();
    time_t now = time(nullptr);
    tm utc{};
    gmtime_r(&now, &utc);
    char date[80]{};
    strftime(date, sizeof(date), "%a, %d %b %Y %H:%M:%S GMT", &utc);
    Buffer response = "HTTP/1.1 200 OK\r\nDate: ";
    response += date;
    response +=
        "\r\nServer: Edoyun/1.0\r\nContent-Type: application/json; charset=utf-8\r\nConnection: "
        "close\r\nContent-Length: ";
    response += std::to_string(json.size());
    response += "\r\nX-Content-Type-Options: nosniff\r\n\r\n";
    return response + json;
}
```

### 12.1 JSON 与 HTTP 是两层

JSON 包含 status 与 message。成功 message 为 success，失败使用统一中文提示。当前 HTTP 起始行固定 `HTTP/1.1 200 OK`，失败分类仍通过 JSON status 表达。

### 12.2 Content-Length 为什么最后计算

先序列化 Json::Value，再取 json.size()。序列化可能加入缩进和换行，UTF-8 中文又占多个字节；必须按真正输出的正文计算，不能按字段个数、字符个数或某个手写模板估算。

### 12.3 空行和 Date

头行使用 CRLF，最后一个空行结束头部，之后才是 JSON。Date 使用 gmtime_r 与 GMT 格式；Connection: close 表达当前短连接策略。

## 13. 发送 Buffer 的寿命

MakeResponse 返回的临时 Buffer 在 Send 调用期间仍活着。当前 send/read 是同步系统调用，即使 socket 非阻塞，也不是把用户缓冲地址交给一个以后才完成的 Overlapped 操作。

Send 返回后，临时 Buffer 可以结束寿命；若部分发送后因 EAGAIN 返回失败，内核不再借用该用户 Buffer，但应用也已没有保存余量以便续写。内存安全的调用寿命与完整交付语义要分开理解。

ThreadFunc 在 Received 返回后移除客户端，即使 Send 返回错误，也没有自动排队补发。

## 14. 校验通过与完整认证系统的区别

当前没有 TLS、标准 HMAC、时间窗口、已用 salt 记录、token 或会话。原请求可被再次提交，time/salt 名称本身不构成重放保护。MD5 的适用限制见 [RFC 6151](https://www.rfc-editor.org/rfc/rfc6151.html)。

这个成功结果精确表示：按当前查到的记录与 key 计算的摘要，等于请求所给摘要。它没有自动让后续连接获得已登录身份，也没有开启播放服务。

## 15. 业务设计的变化位置

改路由主要改业务 HttpParser；改算法涉及 Crypto 和协议双方；改存储涉及客户端、表方言、Escape 以及字段访问。这些变化仍集中在同一个业务类中。

接入框架已经通过 CBusiness 隔离具体入口，不等于登录内部的 HTTP、存储和规则也完全解耦。阶段十一会沿这条事实分析设计模式和演进。
