# EPlayerServer 阶段五 日志系统完整链路

本章把一条日志从调用点跟踪到文件：先解释记录怎样形成，再解释发送连接、接收循环和关闭。记录构造、网络传输与落盘属于不同职责，也有不同的成功边界。

源码入口：[Logger.h](../inc/Logger.h)、[Logger.cpp](../src/Logger.cpp)、[main 中的 LogProcess](../src/main.cpp)。

## 1. 日志链路中的对象

```mermaid
flowchart LR
    Caller[调用线程 TRACEI 或 LOGI] --> Info[LogInfo 正文与前缀]
    Info --> Trace[静态 Trace]
    Trace --> Client[每线程 Unix 客户端]
    Client --> Server[日志子进程事件循环]
    Server --> Write[WriteLog]
    Write --> File[(FILE 与日志文件)]
```

| 对象 | 所在位置 | 责任 |
| --- | --- | --- |
| LogInfo | 产生事件的线程 | 保存完整记录文本 |
| 线程本地 CSocket | 同一个产生线程 | 把文本发送到日志服务 |
| CLoggerServer | 日志子进程 | 监听、接收和管理文件 |
| 日志接收客户端 map | 日志工作线程 | 拥有已接受的本地连接 |

CLoggerServer::Trace 是静态入口，不必通过服务对象调用；真正持有文件的是另一个进程里的实例。static 不意味着文件或服务对象全局唯一。

## 2. 前缀记录的是哪个现场

Prefix 组合文件名、源码行、函数名、日志等级、时间、PID 和 pthread 标识。宏把 __FILE__、__LINE__、__FUNCTION__、getpid 与 pthread_self 在调用处传入。

因此记录前缀标识事件产生的位置，不是日志接收线程的源码位置。日志文件名在日志服务对象构造时由 GetTimeStr 产生，包含日志进程自己的 PID；一份文件中可以出现父进程与业务进程的不同记录 PID。

等级目前只是标签，没有实现按等级配置过滤。LOG_FATAL/FATAL 记录也不自动调用 exit 或抛出异常。

## 3. 格式化调用与流式调用

| 写法 | 构造方式 | 提交时机 |
| --- | --- | --- |
| TRACEI("count=%d", count) | 带格式串和可变参数 | 宏显式调用 Trace |
| LOGI << "count=" << count | 自动提交型 LogInfo | 对象析构调用 Trace |
| DUMPI(data, size) | LogData 标签构造 | 宏显式调用 Trace |

bAuto 区分这些路径。格式化对象和转储对象默认 false，析构不会重复提交；流式对象置 true。

## 4. 可变参数构造的源码

```cpp
LogInfo::LogInfo(char const* file,
                 int line,
                 char const* function,
                 pid_t pid,
                 pthread_t tid,
                 int level,
                 char const* format,
                 ...)
    : m_buf(Prefix(file, line, function, pid, tid, level))
{
    va_list arguments;
    va_start(arguments, format);
    va_list copy;
    va_copy(copy, arguments);
    int size = vsnprintf(nullptr, 0, format, copy);
    va_end(copy);
    if (size >= 0)
    {
        std::vector<char> text(static_cast<size_t>(size) + 1);
        vsnprintf(text.data(), text.size(), format, arguments);
        m_buf.append(text.data(), static_cast<size_t>(size));
    }
    va_end(arguments);
    m_buf += '\n';
}
```

### 4.1 固定参数与 ...

file、line 等固定参数形成前缀，format 指示后面参数如何解释。`...` 不保存类型描述，vsnprintf 根据 `%s`、`%d` 等逐项读取；调用方类型不匹配不能被 va_list 自动修复。

### 4.2 va_start、va_copy、va_end

| 调用 | 作用 |
| --- | --- |
| va_start(arguments, format) | 建立从最后固定参数之后访问实参的遍历状态 |
| va_copy(copy, arguments) | 创建可独立消费的遍历状态 |
| va_end(copy) | 完成副本的清理 |
| va_end(arguments) | 完成原遍历状态的清理 |

va_list 不是最终字符串，也不能通用地用普通赋值替代 va_copy。一次格式化可能推进其状态，第一遍用副本，第二遍才能从原始状态读取。

## 5. 两遍格式化逐步推演

输入为 `"user=%s count=%d", "bit", 12`，正文应为 `user=bit count=12`，共 17 字节。

```text
前缀已经放入 m_buf
  → 对 copy 调用 vsnprintf(nullptr, 0, ...)
  → 得到 size=17
  → vector 创建 18 个 char
  → 对 arguments 真正格式化
  → 缓冲含 17 正文字节和 1 个终止零
  → append 前 17 字节
  → 追加换行
```

### 5.1 size 到底计什么

size 是所需正文字节数，不是 sizeof(va_list)、copy 长度或参数个数；不含终止零、已有前缀和最后换行。负数表示格式化失败，先判断再转 size_t，避免负值变为巨大无符号分配量。

### 5.2 为什么需要 vector

vsnprintf 不申请目标缓冲。第一次调用只计算需要，vector 负责申请 size+1 存储并自动释放，第二次调用写入。最后 append 不把终止零算入记录。

| 函数 | 谁准备内存 | 长度能力 |
| --- | --- | --- |
| vsprintf | 调用者 | 无目标长度参数 |
| vsnprintf | 调用者 | 限制写入空间，并返回所需长度 |
| vasprintf | 函数分配并通过 char** 返回 | 调用者事后 free，属于 GNU 接口 |

当前实现使用第二种。接口语义可对照 [printf](https://man7.org/linux/man-pages/man3/printf.3.html) 与 [asprintf](https://man7.org/linux/man-pages/man3/asprintf.3.html) 手册。

## 6. 流式追加与析构提交

operator<< 每次创建 ostringstream，把传入值写进去，再追加 stream.str()，返回当前 LogInfo&，因此能继续链式追加。

```cpp
LogInfo::~LogInfo()
{
    if (bAuto)
    {
        m_buf += '\n';
        CLoggerServer::Trace(*this);
    }
}
```

通常 `LOGI << "connected";` 中，分号结束完整表达式，临时对象析构并发送一次。命名对象则活到作用域结束。

### 6.1 两种 auto 写法并不等价

```cpp
auto info = LOGI;
info << "connected";
```

这是一个命名对象，稍后作用域结束才提交。另一种：

```cpp
auto info = LOGI << "connected";
```

右边 operator<< 返回左值引用，auto 按值复制 LogInfo。原临时对象在分号处提交，副本之后析构又提交；当前隐式复制没有删除或转移自动提交责任。

流式接口的便利依赖生命周期，保存表达式时应同时判断是否发生复制，以及自动提交责任是否也被复制。

## 7. 二进制转储为什么带长度

LogData 保存 const void* 和 size_t。构造循环每行显示最多 16 字节，十六进制旁边显示可打印字符，其他字节以点代替。

输入可能含零，不能用 strlen。最后一行可能不足 16 字节，每次访问都需检查 `offset+i<size`。调用中给出地址但没有正确长度，日志模块也无法判断实际有效内存范围。

## 8. Trace 与每线程连接

```cpp
static void Trace(LogInfo const& info)
{
    static thread_local std::unique_ptr<CSocket> client;
    static thread_local pid_t owner = -1;
    if (!client || owner != getpid())
    {
        client = std::make_unique<CSocket>();
        owner = getpid();
        if (client->Init(CSockParam("./log/server.sock", 0)) != 0 || client->Link() != 0)
        {
            client.reset();
            return;
        }
    }
    if (client->Send(info) != 0)
        client.reset();
}
```

### 8.1 两个 thread_local

client 每线程一份，复用已建立的 Unix 连接；owner 保存创建连接时的 PID。fork 后若继承了旧线程局部状态，PID 变化会触发重新初始化，避免子进程继续把旧客户端当作自己创建的连接。

调用 static 函数不会自动产生线程，Trace 仍在记录产生者的线程运行。该连接没有设置非阻塞，所以发送可能等待内核缓冲。

### 8.2 失败后的语义

Init、Link 失败就清空并返回；Send 失败也清空。下一次日志可再建立连接，但失败的上一条记录没有被缓存和重放，调用者也拿不到逐条写入确认。

连接复用与可靠送达是两项不同能力，不能由“以后重连”推出“之前的记录也会补回”。

## 9. 日志服务怎样启动

```cpp
int Start()
{
    if (m_server)
        return -1;
    if (mkdir("log", 0755) != 0 && errno != EEXIST)
        return -2;
    m_file = fopen(m_path, "ab");
    if (!m_file)
        return -3;
    if (m_epoll.Create(1) != 0)
    {
        Close();
        return -4;
    }
    m_server = new CSocket();
    int result = m_server->Init(CSockParam("./log/server.sock", SOCK_ISSERVER));
    if (result != 0 || m_epoll.Add(*m_server, EpollData(m_server)) != 0)
    {
        Close();
        return -5;
    }
    m_running = true;
    if (m_thread.Start() != 0)
    {
        Close();
        return -6;
    }
    return 0;
}
```

Start 顺序为建目录、打开文件、创建 epoll、创建 Unix 监听、登记监听、置运行标志、启动线程。main 的 LogProcess 随后把结果通过控制通道通知父进程。

日志监听使用 `./log/server.sock`，父子进程共享继承的工作目录；从不同目录启动不同实例会使用不同的相对地址，调试工作目录也决定文件位置。

## 10. 接收循环怎样区分监听和客户端

```cpp
int ThreadFunc()
{
    std::map<int, std::unique_ptr<CSocketBase>> clients;
    EPEvents events;
    while (m_running)
    {
        ssize_t count = m_epoll.WaitEvents(events, 50);
        if (count < 0)
            break;
        for (ssize_t i = 0; i < count; ++i)
        {
            auto* socket = static_cast<CSocketBase*>(events[i].data.ptr);
            if (socket == m_server)
            {
                CSocketBase* client = nullptr;
                if (m_server->Link(&client) != 0)
                    continue;
                int descriptor = *client;
                if (m_epoll.Add(descriptor, EpollData(client), EPOLLIN | EPOLLRDHUP) != 0)
                    delete client;
                else
                    clients[descriptor].reset(client);
            }
            else if (socket)
            {
                int descriptor = *socket;
                Buffer data(4096);
                int result = socket->Recv(data);
                if (result <= 0)
                {
                    m_epoll.Del(descriptor);
                    clients.erase(descriptor);
                }
                else
                    WriteLog(data);
            }
        }
    }
    return 0;
}
```

| 事件对象 | 判别 | 动作 |
| --- | --- | --- |
| 监听对象 | data.ptr == m_server | accept，再登记新客户端 |
| 客户端 | 其他有效对象指针 | Recv，读到后写文件，失效则移除 |

clients 用 unique_ptr 拥有客户端包装，epoll 的 ptr 只借用。按 FD 保存拥有者、按 ptr 分发事件，是两个不同用途的索引。

正常退出循环时局部 clients 析构，释放余下连接；Close 先停止线程，再关闭 epoll、监听和文件。

## 11. 写入与记录边界

WriteLog 调用 fwrite(data.data(), 1, data.size(), file)，按字节写当前收到的内容，再 fflush。

日志使用 SOCK_STREAM：

```text
生产端一条长记录 A
  → 接收片段 A1
  → 此时处理另一连接的记录 B
  → 接收片段 A2
  → 文件可能为 A1、B、A2
```

集中写入避免本实现多个写线程竞争 FILE，不自动保证来自不同连接的整条记录不交错。当前没有长度帧、记录编号或重组缓冲。

fflush 交出 C 库缓冲，不等于 fsync 持久化；当前也未检查每次 fwrite/fflush 的完整错误结果。

## 12. 正常关闭和未提供的保证

```cpp
int Close()
{
    m_running = false;
    m_thread.Stop();
    m_epoll.Close();
    delete m_server;
    m_server = nullptr;
    if (m_file)
    {
        fclose(m_file);
        m_file = nullptr;
    }
    return 0;
}
```

main 先停止业务与接入，再停止日志，减少收尾记录发送到已关闭服务的机会。但没有日志排空回执，也没有保证所有在途片段都被接收后才关闭。

```text
构造成功 ≠ 发送成功 ≠ 日志进程收到
         ≠ fwrite 完成 ≠ 持久化完成
```

这些不同里程碑解释了为何日志可以辅助观察，却不能单独作为所有请求都已完成的证明。

## 13. 模块设计的含义

LogInfo 隔离文本构造，Trace 隔离发送入口，CLoggerServer 隔离文件责任；thread_local 减少生产端共享客户端的锁需求。流式对象用析构触发副作用，资源对象用析构清理，两者有共同的生命周期基础，但职责不同。
