# EPlayerServer 阶段四 回调线程与任务池

本章把函数、任务、线程和事件循环分开。项目通过可调用对象保存工作，通过 CThread 创建执行者，通过 CThreadPool 安排执行；当前应用又让工作线程长期运行 epoll 循环。

源码入口：[Function.h](../inc/Function.h)、[Thread.h](../inc/Thread.h)、[Thread.cpp](../src/Thread.cpp)、[ThreadPool.h](../inc/ThreadPool.h)、[CServer.h](../inc/CServer.h)。

## 1. 为什么需要保存一个调用

线程池可能接受普通函数，也可能接受成员函数。后者还需要接收对象和参数。若线程池为每个类型写一个分支，它就会依赖每个业务类。

统一机制为：

```text
函数指针 + 接收对象 + 参数
  → 绑定成以后可执行的对象
  → 通过统一接口保存
  → 在选定执行者上调用
```

函数对象保存“调用关系”，不自动延长绑定裸指针所指对象的寿命。

回调就是先把函数及所需上下文登记下来，再由另一段流程在条件满足时调用。它描述调用时机的组织方式；实际运行在哪条线程，要沿触发处的调用栈判断。本项目的 Received 由业务事件线程直接调用，仍在同一条线程内执行。

## 2. CFunctionBase 与类型擦除

CFunctionBase 有虚析构和三个虚 operator()：无参、socket 参数、socket 加 Buffer 参数。不同派生包装覆盖不同签名。

| 包装 | 覆盖的调用形状 | 当前使用者 |
| --- | --- | --- |
| CFunction | int operator()() | 进程入口、线程入口、池任务 |
| CConnectedFunction | int operator()(CSocketBase*) | 连接通知 |
| CReceivedFunction | int operator()(CSocketBase*, Buffer const&) | 完整请求通知 |

基类未覆盖的默认重载返回 -1，并不是编译期禁止误用。一个基类统一多签名的简化，也使某些错误被留到运行期。

CFunction 的 m_binder 类型由模板参数确定，operator() 再执行 m_binder()。调用方只看到 CFunctionBase*，这是类型擦除，不是把所有调用都变成同一种实际函数类型。

关键包装在 Function.h 中只有这一层：

```cpp
template <typename _FUNCTION_, typename... _ARGS_>
class CFunction : public CFunctionBase
{
public:
    CFunction(_FUNCTION_ func, _ARGS_... args)
        : m_binder{std::forward<_FUNCTION_>(func), std::forward<_ARGS_>(args)...}
    {
    }
    virtual ~CFunction()
    {
    }
    virtual int operator()()
    {
        return m_binder();
    }
    typename std::_Bindres_helper<int, _FUNCTION_, _ARGS_...>::type m_binder;
};
```

以 `AddTask(&CServer::ThreadFunc, this)` 为例，模板得到的函数类型是成员函数指针，参数类型是 CServer*。binder 保存这两项，稍后无参调用 m_binder() 时，就会对保存的对象调用 ThreadFunc。线程池只需持有基类并执行 `(*task)()`，具体成员调用由虚函数进入这份包装后完成。

## 3. 成员函数与占位参数

```cpp
m_pool.AddTask(&CServer::ThreadFunc, this);
setConnectedCallback(&CEdoyunPlayerServer::Connected, this, _1);
setRecvCallback(&CEdoyunPlayerServer::Received, this, _1, _2);
```

| 部分 | 在什么时候确定 |
| --- | --- |
| 成员函数地址 | 建立绑定时 |
| this 接收对象 | 建立绑定时 |
| _1、_2 对应实参 | 事件真正触发时 |

无参任务已经绑定全部实参；连接回调仍等待实际 socket；接收回调再等待完整数据。Args... 是编译时参数包，va_list 则是日志中的运行时不定参数机制，两者不能混同。

当前绑定依赖 std::_Bindres_helper，是标准库实现细节；外部参数多按值接收，也不是完整完美转发接口。

## 4. CThread 的资源状态

| 字段 | 表达什么 |
| --- | --- |
| m_function | 拥有保存的无参调用 |
| m_thread | pthread 标识 |
| m_running | 包装层认为入口尚在执行 |
| m_joinable | 还需要等待并回收这条线程 |
| m_paused | 暂停意图 |
| m_current | 当前线程的 thread_local CThread 指针 |

运行结束不等于已经 join。即使 m_running=false，m_joinable 仍可能为 true，Stop 仍要回收线程资源。

## 5. C 入口怎样调用 C++ 对象

pthread_create 接受普通函数指针，不能直接接受带隐藏 this 的非静态成员函数。项目的桥接为：

```cpp
static void* ThreadEntry(void* argument)
{
    auto* self = static_cast<CThread*>(argument);
    m_current = self;
    (*self->m_function)();
    self->m_running = false;
    m_current = nullptr;
    return nullptr;
}
```

argument 是 pthread_create 最后传入的 this。静态入口把它转回对象，执行保存的任务，完成后更新包装状态。

这是一条普通函数调用链，不是再创建一条新线程。ThreadEntry 已经在 pthread 创建的执行线程中运行。

## 6. Start 的接口与错误约定

```cpp
int Start()
{
    if (m_joinable || !m_function)
        return -1;
    std::call_once(m_signalOnce, [] {
        struct sigaction action{};
        action.sa_handler = &CThread::PauseSignal;
        sigemptyset(&action.sa_mask);
        sigaction(SIGUSR1, &action, nullptr);
    });
    m_running = true;
    int result = pthread_create(&m_thread, nullptr, &CThread::ThreadEntry, this);
    if (result != 0)
    {
        m_running = false;
        return -result;
    }
    m_joinable = true;
    return 0;
}
```

pthread_create 的四个参数依次是输出线程标识、线程属性、静态入口、入口参数。nullptr 属性使用默认设置。返回值非零时直接是错误号，不能只按 errno 的通用模式理解。

call_once 安装 SIGUSR1 暂停处理器。Pause 使用信号和 thread_local 指针控制轮询，正常服务路径未使用它；持锁线程被任意暂停会阻塞其他线程，它不是通用安全挂起工具。

## 7. 线程池保存的不是连接

```text
CThreadPool
  ├─ vector<unique_ptr<CThread>> 工作线程
  ├─ deque<unique_ptr<CFunctionBase>> 待执行任务
  ├─ mutex 保护队列和停止谓词
  ├─ condition_variable 让空队列消费者休眠
  └─ bool m_stopping
```

这里没有 ClientState map，也没有 MySQL 连接。它只组织可调用任务，连接管理由服务对象完成。

## 8. Start 怎样建立固定执行者

```cpp
int Start(unsigned count)
{
    if (!m_threads.empty() || count == 0)
        return -1;
    m_stopping = false;
    for (unsigned i = 0; i < count; ++i)
    {
        auto thread = std::make_unique<CThread>(&CThreadPool::TaskDispatch, this);
        if (thread->Start() != 0)
        {
            Close();
            return -2;
        }
        m_threads.push_back(std::move(thread));
    }
    return 0;
}
```

count 为固定工作线程数，0 被拒绝。每条 CThread 绑定同一个 TaskDispatch 与同一个池对象。成功创建的线程可能已经在等待条件变量，后续任务进入队列才执行。

若中途失败，Close 清理此前已建立的线程。这说明初始化不是单个布尔动作，而是逐步取得资源并可能需要回滚。

## 9. AddTask 的所有权转移

```cpp
template <typename Function, typename... Args>
int AddTask(Function function, Args... args)
{
    auto task = std::make_unique<CFunction<Function, Args...>>(function, args...);
    {
        std::lock_guard<std::mutex> lock(m_mutex);
        if (m_stopping || m_threads.empty())
            return -1;
        m_tasks.push_back(std::move(task));
    }
    m_ready.notify_one();
    return 0;
}
```

| 步骤 | 锁与所有权 |
| --- | --- |
| 创建 task | 局部 unique_ptr 独占 |
| 检查停止和线程数组 | 持 m_mutex |
| push_back(move(task)) | 所有权转入队列 |
| 释放锁 | 入队已完成 |
| notify_one | 唤醒可能休眠的消费者 |

AddTask 返回 0 只确认入队；没有 future，也不收集任务最后的 int 返回值。任务对象分配等异常也没有统一转换成这些负数返回码。

## 10. TaskDispatch 的锁作用域

```cpp
int TaskDispatch()
{
    for (;;)
    {
        std::unique_ptr<CFunctionBase> task;
        {
            std::unique_lock<std::mutex> lock(m_mutex);
            m_ready.wait(lock, [this] { return m_stopping || !m_tasks.empty(); });
            if (m_stopping && m_tasks.empty())
                return 0;
            task = std::move(m_tasks.front());
            m_tasks.pop_front();
        }
        (*task)();
    }
}
```

### 10.1 wait 的两个参数

| 参数 | 作用 |
| --- | --- |
| lock | 当前持有 m_mutex 的 unique_lock |
| predicate，即条件判断函数 | 停止或队列非空时允许继续 |

wait 在休眠前原子地释放锁，返回前重新取得锁，谓词被重新检查。通知本身不保存任务数量，队列保存事实；虚假唤醒也不能绕开队列检查。

### 10.2 取出与执行分离

局部 task 先获得队头所有权，再 pop_front。内层花括号结束后队列锁释放，外层才调用任务。

假设任务 A 花五秒：如果执行时持队列锁，其他线程既不能取 B，生产者也不能提交 C。当前锁范围只保护池状态，因此 A 不会以这把队列锁阻塞其他任务调度。

### 10.3 简单队列推演

```text
队列初始 [A, B]
worker 1 取 A → 队列 [B] → 解锁执行 A
worker 2 取 B → 队列 []  → 解锁执行 B
producer 加 C → 队列 [C] → 通知消费者
```

FIFO 指成功入队的次序，不保证 A 比 B 更早完成。多个消费者的执行时长不同，完成顺序可反过来。

## 11. 当前服务提交的是长期循环

| 池 | 入队任务 | 工作期间 |
| --- | --- | --- |
| CServer 池 | 两个 ThreadFunc | 等待监听就绪、accept、转交 |
| 业务池 | N 个 ThreadFunc | 等待客户端、读、解析、查询与响应 |

任务不返回时，TaskDispatch 不再从队列取下一项。因此当前程序并不是把每次 HTTP 请求单独放进池。数据库慢查询也仍占用这条事件线程。

真实调用栈：

```text
CThread::ThreadEntry
  → 保存 TaskDispatch 的 CFunction::operator()
  → CThreadPool::TaskDispatch
  → 保存业务 ThreadFunc 的 CFunction::operator()
  → CEdoyunPlayerServer::ThreadFunc
  → CReceivedFunction::operator()(socket, data)
  → CEdoyunPlayerServer::Received
  → 登录解析、响应构造和 Send
```

这些层次运行在同一个工作线程中。父进程 main 的 Run 只是等待停止，不负责执行 epoll 分发。

## 12. 两个回调实际在哪触发

| 回调 | 注册位置 | 触发位置 | 线程 |
| --- | --- | --- | --- |
| Connected | BusinessProcess | 保存连接之后、epoll Add 之前 | 业务主线程 |
| Received | BusinessProcess | ThreadFunc 确认请求完整后 | 业务工作线程 |

CBusiness 保存回调槽，具体业务类同时提供登记和触发代码；CServer 父进程只转交连接，不触发 HTTP 回调。这是一种局部事件回调组织，尚不是独立的通用协议框架。

每种回调只有一个槽，setter 替换旧对象。与设计模式的关系留到阶段十一统一分析；这里先确认谁登记、谁触发和谁拥有回调包装。

## 13. 停止字段属于不同层次

```text
服务层 m_stop / m_stopping → 长期事件循环的退出条件
池的 m_stopping           → 消费者是否停止等待或退出
线程 m_running           → CThread 包装层状态
```

改写 CThread::m_running 不会让任意绑定函数自动返回。当前正常关闭先设置服务层退出条件，再 Close 池，使执行中的长期循环和池自身都能收尾。

## 14. Close 与取消的语义

```cpp
void Close()
{
    {
        std::lock_guard<std::mutex> lock(m_mutex);
        m_stopping = true;
    }
    m_ready.notify_all();
    for (auto& thread : m_threads)
        thread->Stop();
    m_threads.clear();
    std::lock_guard<std::mutex> lock(m_mutex);
    m_tasks.clear();
}
```

```cpp
int Stop()
{
    if (!m_joinable)
        return 0;
    if (pthread_equal(pthread_self(), m_thread))
        return -1;
    m_running = false;
    m_paused = false;
    timespec deadline{};
    clock_gettime(CLOCK_REALTIME, &deadline);
    deadline.tv_nsec += 100000000;
    if (deadline.tv_nsec >= 1000000000)
    {
        ++deadline.tv_sec;
        deadline.tv_nsec -= 1000000000;
    }
    int result = pthread_timedjoin_np(m_thread, nullptr, &deadline);
    if (result == ETIMEDOUT)
    {
        pthread_cancel(m_thread);
        result = pthread_join(m_thread, nullptr);
    }
    if (result != 0)
        return -result;
    m_joinable = false;
    m_thread = 0;
    return 0;
}
```

Stop 先限时等待约 100 ms，超时再 pthread_cancel 并 join。请求取消不保证任意 CPU 循环立即停止，join 也不提供相同的严格时间上限。

虽然 TaskDispatch 在停止且队列非空时还能取任务，Close 随后又停止各线程并清空队列，所以对外没有严格的“所有提交任务必然完成”保证。当前应结合服务退出标志理解正常路径，而不是仅凭队列谓词推导完全排空。

## 15. 设计落点

任务对象对应 Command 的轻量形式；队列、锁和条件变量形成生产者消费者组织；静态入口适配 C 的线程 API；unique_ptr 管理任务与线程包装的删除责任。

这些机制解决执行安排，不替代连接解析状态和数据库同步。下一章用相同的 socket、epoll 和线程设施，组成独立日志服务。
