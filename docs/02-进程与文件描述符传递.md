# EPlayerServer 阶段二 进程与文件描述符传递

前一章区分了指针、包装对象和内核资源。本章解释这些实体在 fork 后怎样变化，以及父进程如何把后来 accept 的连接交给已经存在的业务子进程。

源码入口：[Process.h](../inc/Process.h)、[Function.h](../inc/Function.h)、[main.cpp](../src/main.cpp)、[CServer.cpp](../src/CServer.cpp)。

## 1. 需要解决的三件事

```text
创建执行单元：让业务与日志在各自进程中执行。
建立启动协议：确认子进程已经准备好，而非只是 PID 已出现。
交付连接能力：把父进程的新 socket 引用交给业务进程。
```

CProcess 同时保存入口、PID、通信端点和就绪状态，因而既是进程包装，也承载了本项目特定的父子通信协议。

## 2. fork 返回之后发生什么

| fork 返回值 | 当前执行者 | 下一步 |
| --- | --- | --- |
| 小于 0 | 创建失败的父进程 | 清理通道并返回错误 |
| 等于 0 | 新子进程 | 关闭父端，执行绑定入口 |
| 大于 0 | 原父进程 | 保存子 PID，关闭子端并返回 |

子进程从 fork 返回位置继续，不会重新从 main 第一行开始。地址空间的普通对象是副本，Linux 写时复制减少复制成本，却不改变之后的内存隔离。fork 的接口语义见 [Linux 手册](https://man7.org/linux/man-pages/man2/fork.2.html)。

### 2.1 为什么保存的 this 仍可用

绑定入口是在 fork 前建立的。函数对象、业务对象及其地址都包含在当时的地址空间中，子进程可以访问自己的那份对象。指针不是通过 socket 消息传过去的。

之后父进程更改其 business 成员，不会更新子进程。子进程创建 MySQL 连接，也不会把父进程的 m_db 改为有效。两个事实都来自同一隔离规则。

这里的地址空间复制由操作系统完成，不会逐个调用 C++ 拷贝构造函数。因此 CProcess 禁止 C++ 按值复制，仍然可以出现在 fork 时继承的地址空间中。普通 shared_ptr 的控制块也随内存分开；它不能靠引用计数管理父子进程共同拥有的 C++ 对象。

### 2.2 多线程与 fork 的时序

fork 后，子进程只保留调用 fork 的那条线程。其他线程若曾持有锁，其内存状态可能被复制，但持锁线程已不在子进程中。当前主线在父进程启动接入线程前完成两个 fork，避免把自己的运行中线程池复制进子进程。

这一安排是当前启动顺序的理由，不能扩展成“任意多线程程序里都可在 fork 后继续调用复杂 C++”的通用保证。

## 3. CProcess 保存的状态

| 成员 | 初始值 | 责任 |
| --- | --- | --- |
| m_func | nullptr | 拥有可调用入口对象 |
| m_pid | -1 | 父进程记录待回收的子 PID |
| m_socketFds[0] | -1 | fork 后供子进程使用 |
| m_socketFds[1] | -1 | fork 后供父进程使用 |
| m_notified | false | 子入口是否已经主动报告就绪 |

SetEntryFunction 创建新的 CFunction，替换旧入口；当 m_pid>0 时拒绝改入口。创建一个入口对象不等于立刻执行它。

## 4. 创建子进程的完整步骤

```cpp
int CreateSubProcess()
{
    if (!m_func || m_pid > 0)
        return -1;
    for (int& descriptor : m_socketFds)
    {
        if (descriptor >= 0)
            close(descriptor);
        descriptor = -1;
    }
    m_notified = false;
    if (socketpair(AF_UNIX, SOCK_SEQPACKET | SOCK_CLOEXEC, 0, m_socketFds) != 0)
        return -2;
    m_pid = fork();
    if (m_pid < 0)
    {
        close(m_socketFds[0]);
        close(m_socketFds[1]);
        m_socketFds[0] = m_socketFds[1] = -1;
        return -3;
    }
    if (m_pid == 0)
    {
        close(m_socketFds[1]);
        m_socketFds[1] = -1;
        // Ctrl+C 由父进程统一处理，再通过 IPC 通知子进程清理并退出。
        signal(SIGINT, SIG_IGN);
        signal(SIGTERM, SIG_DFL);
        int result = (*m_func)();
        if (!m_notified)
            NotifyReady(result);
        _exit(result == 0 ? 0 : 1);
    }
    close(m_socketFds[0]);
    m_socketFds[0] = -1;
    return 0;
}
```

### 4.1 socketpair 的参数

| 参数 | 当前值 | 意义 |
| --- | --- | --- |
| 域 | AF_UNIX | 本机通信 |
| 类型 | SOCK_SEQPACKET | 有序并保留消息边界 |
| 附加属性 | SOCK_CLOEXEC | exec 新程序时关闭相应描述符 |
| 输出数组 | m_socketFds | 两个已连接端点 |

CLOEXEC 不表示 fork 时不继承；本程序也没有在子分支 exec 别的程序。双方 fork 后显式关闭不用的一端，才能让各自端点职责清楚，并使对端关闭更容易被观察。

### 4.2 端点方向

```text
父进程保留 [1]                     子进程保留 [0]
    SendSocket / SendFD  ───────────────→ RecvSocket / RecvFD
    WaitReady            ←────────────── NotifyReady
```

同一连接可以双向使用。数组下标是项目约定，不是 socketpair 自动规定的发送端和接收端。

### 4.3 入口结束之后

子分支在入口返回后检查 m_notified；未通知时补发入口返回值，再将成功/失败压缩为 _exit(0) 或 _exit(1)。子进程不会返回 CServer::Init 的父路径继续监听。

SIGINT 在子分支被忽略，正常运行由父进程接收 Ctrl+C 并协调停止；SIGTERM 恢复默认行为，供后备终止使用。具体停机流程放在阶段十。

## 5. 就绪与创建是两个里程碑

```cpp
int NotifyReady(int status)
{
    m_notified = true;
    return send(m_socketFds[0], &status, sizeof(status), MSG_NOSIGNAL) == sizeof(status) ? 0
                                                                                         : -1;
}
```

```cpp
int WaitReady(int timeout = 5000)
{
    pollfd event{m_socketFds[1], POLLIN, 0};
    int result;
    do
    {
        result = poll(&event, 1, timeout);
    } while (result < 0 && errno == EINTR);
    if (result <= 0)
        return -1;
    int status = -1;
    return recv(m_socketFds[1], &status, sizeof(status), 0) == sizeof(status) ? status : -1;
}
```

NotifyReady 的 status 是模块初始化结果，0 表示成功。WaitReady 的 timeout 单位是毫秒，默认 5000；poll 等待父端可读，再接收一个 int。

| 时间点 | 可以得出的结论 |
| --- | --- |
| socketpair 成功 | 本地控制通道存在 |
| fork 成功 | 子执行流已经创建 |
| 日志 NotifyReady(0) | 文件、监听和日志线程初始化完成 |
| 业务 NotifyReady(0) | 数据库、表、epoll 和任务提交完成 |
| 父进程开始监听 | 接入设施已继续初始化 |

就绪不是持续健康检查；工作循环后来退出时，父进程没有独立心跳或自动重启机制。断点若长时间停在 NotifyReady 之前，也会让父进程的等待超时。

## 6. FD 的整数为什么不能直接发过去

```text
父进程的 12 → 父 FD 表第 12 项 → 内核连接 A
子进程的 12 → 子 FD 表第 12 项 → 可能是完全不同的对象
```

普通 send 把 int 12 作为四个字节发送，只传了数字，没有安装子进程的 FD 表项。fork 能继承的是 fork 当时已经打开的描述符，不能继承后来 accept 的连接。

正确传递需要 SCM_RIGHTS：内核根据辅助消息，为接收进程取得同一打开对象的引用，接收 FD 的数字可与发送 FD 不同。详见 [Unix socket 手册](https://man7.org/linux/man-pages/man7/unix.7.html)。

## 7. SendSocket 的消息布局

```cpp
int SendSocket(int descriptor, sockaddr_in const* address)
{
    sockaddr_in payload{};
    if (address)
        payload = *address;
    iovec vector{&payload, sizeof(payload)};
    alignas(cmsghdr) char control[CMSG_SPACE(sizeof(int))]{};
    msghdr message{};
    message.msg_iov = &vector;
    message.msg_iovlen = 1;
    if (descriptor >= 0)
    {
        message.msg_control = control;
        message.msg_controllen = sizeof(control);
        cmsghdr* header = CMSG_FIRSTHDR(&message);
        header->cmsg_level = SOL_SOCKET;
        header->cmsg_type = SCM_RIGHTS;
        header->cmsg_len = CMSG_LEN(sizeof(int));
        memcpy(CMSG_DATA(header), &descriptor, sizeof(descriptor));
    }
    ssize_t sent;
    do
    {
        sent = sendmsg(m_socketFds[1], &message, MSG_NOSIGNAL);
    } while (sent < 0 && errno == EINTR);
    return sent == sizeof(payload) ? 0 : -1;
}
```

### 7.1 普通载荷与辅助载荷

| 对象 | 当前内容 | 作用 |
| --- | --- | --- |
| payload | sockaddr_in | 带客户端地址，提供固定普通载荷 |
| iovec | 地址和长度 | 指定普通载荷的内存范围 |
| control | CMSG_SPACE(sizeof(int)) 字节 | 容纳描述符辅助消息及对齐 |
| cmsghdr | SOL_SOCKET、SCM_RIGHTS | 告诉内核按描述符引用解释数据 |
| msghdr | iovec 与 control 的描述 | 一次交给 sendmsg |

CMSG_SPACE 为整个暂存区计算对齐后的占用，CMSG_LEN 表示辅助消息本身长度；两者用途不同。对齐声明让 cmsghdr 可以正确访问这块字符存储。

### 7.2 EINTR、MSG_NOSIGNAL 和返回码

sendmsg 被信号打断时循环重试。MSG_NOSIGNAL 避免向已关闭对端发送时产生 SIGPIPE 终止当前进程，错误仍通过返回值表达。

成功条件是发送字节数等于普通 payload 长度。0 返回值只表示消息交给通道，不是业务进程已经完成 ClientState 登记的确认。

## 8. RecvSocket 怎样恢复引用

```cpp
int RecvSocket(int& descriptor, sockaddr_in* address)
{
    descriptor = -1;
    sockaddr_in payload{};
    iovec vector{&payload, sizeof(payload)};
    alignas(cmsghdr) char control[CMSG_SPACE(sizeof(int))]{};
    msghdr message{};
    message.msg_iov = &vector;
    message.msg_iovlen = 1;
    message.msg_control = control;
    message.msg_controllen = sizeof(control);
    ssize_t received;
    do
    {
        received = recvmsg(m_socketFds[0], &message, MSG_CMSG_CLOEXEC);
    } while (received < 0 && errno == EINTR);
    if (received != sizeof(payload) || (message.msg_flags & (MSG_TRUNC | MSG_CTRUNC)))
        return -1;
    if (address)
        *address = payload;
    for (cmsghdr* header = CMSG_FIRSTHDR(&message); header;
         header = CMSG_NXTHDR(&message, header))
    {
        if (header->cmsg_level == SOL_SOCKET && header->cmsg_type == SCM_RIGHTS &&
            header->cmsg_len >= CMSG_LEN(sizeof(int)))
        {
            memcpy(&descriptor, CMSG_DATA(header), sizeof(descriptor));
            break;
        }
    }
    return 0;
}
```

接收前把输出 descriptor 设为 -1，准备同样大小的地址载荷和辅助区。recvmsg 后先检查长度和截断标志，再遍历控制消息，只有 SOL_SOCKET/SCM_RIGHTS 且长度足够才复制出整数。

| 检查 | 排除的问题 |
| --- | --- |
| 普通载荷长度一致 | 错误消息布局或通道关闭 |
| 无 MSG_TRUNC | 普通消息未被截断 |
| 无 MSG_CTRUNC | 控制信息未被截断 |
| 匹配 level 和 type | 不把其他控制消息误当作 FD |
| CMSG_LEN 足够 | 不读取不足一个 int 的内容 |

MSG_CMSG_CLOEXEC 给收到的新 FD 设置 exec 时关闭。函数拿到的是自己的有效引用，不能再把它当作发送方进程的数字索引来理解。

## 9. 转交的所有权时间线

假设父 accept 得到 FD=12，子收到 FD=17：

```text
T0 父进程持有 12
T1 sendmsg 成功，通道内的消息保留内核引用
T2 父进程 delete client，关闭 12
T3 子进程 recvmsg，安装自己的 17
T4 子进程处理 HTTP
T5 最后连接状态释放，关闭 17
```

T2 可以早于 T3，父进程不需要等待子进程完成接收才 close。反过来，若整个接收端消失，发送成功也不保证将来一定处理该连接。

这个流程没有在父子进程间共享 CSocket 对象。父包装对象销毁后，子进程建立自己的包装来管理收到的引用。

## 10. 停止消息为什么得到 -1

SendFD(-1) 调用 SendSocket 时不附带 SCM_RIGHTS，普通地址载荷仍会发送。RecvSocket 预设的 -1 没被控制消息覆盖，调用方就把它解释为停止。

```text
有合法辅助 FD → 新连接
载荷有效但无 FD → 停止
接收失败        → 通道异常，当前入口也退出循环
```

没有把负数 FD 请求内核安装。日志主线程同样等待这一类控制消息，但日志文本本身走另一个 Unix 流式 socket。

## 11. 等待退出与析构不同

```cpp
int Wait(int timeout = 3000)
{
    if (m_pid <= 0)
        return 0;
    int status = 0;
    for (int elapsed = 0; elapsed < timeout; elapsed += 10)
    {
        pid_t result = waitpid(m_pid, &status, WNOHANG);
        if (result == m_pid || (result < 0 && errno == ECHILD))
        {
            m_pid = -1;
            return status;
        }
        if (result < 0 && errno != EINTR)
            return -1;
        usleep(10000);
    }
    kill(m_pid, SIGTERM);
    while (waitpid(m_pid, &status, 0) < 0 && errno == EINTR)
    {
    }
    m_pid = -1;
    return status;
}
```

Wait 在默认约三秒的轮询期使用 WNOHANG，之后发 SIGTERM，再阻塞 waitpid。若子进程不响应 SIGTERM，后半段没有严格超时保证。

成功回收返回的是编码状态，正常退出可先 WIFEXITED，再 WEXITSTATUS 取退出码。_exit(1) 在 Linux 上常见 wait 状态为 256，不是返回业务原来的 -1 或 -2。就绪状态和进程退出状态因此必须分别阅读。参见 [wait 手册](https://man7.org/linux/man-pages/man2/waitpid.2.html)。

CProcess 析构只关闭自己的通道并删除入口对象，不自动 wait。主流程通过显式 Wait 回收子进程，避免把“对象消失”误当成“子进程已回收”。

## 12. 守护化辅助函数的定位

SwitchDeamon 包含 double fork、setsid、关闭标准 FD、umask 和忽略 SIGCHLD。main 没调用它。忽略 SIGCHLD 还会改变当前显式 wait 的预期，因此这个函数不能直接当成已完成的守护部署能力。

| 入口 | 谁调用 | 下一步 |
| --- | --- | --- |
| SetEntryFunction | main 或 CServer::Init | 保存调用对象 |
